Existing Codex chats lose project write access after a folder rename

Recorded October 17, 2026 · America/Los_Angeles (UTC−07:00). App version: not recorded.

Renaming a local project and re-adding it in Codex left existing chats able to read the renamed repository but unable to create files there during the recorded audit. A fresh chat could write to the same directory. The user could not find a supported way to restore the existing chats’ access while retaining their context.

Environment and user actions

The project was known as Plumbing Incorporated and lived at /Users/sfoley/repos/plumbing_inc. It contained a Git repository connected to GitHub. The user renamed the folder to Drain Damage at /Users/sfoley/repos/drain_damage, removed the old project/directory entry from Codex, and added the renamed directory. This report does not claim that the repository was deleted or that operating-system permissions were changed.

Steps to reproduce the reported sequence

  1. Add a local repository to Codex and create multiple chats associated with it.
  2. Rename its containing folder outside the existing chats.
  3. Remove the old project entry in Codex and add the renamed directory.
  4. Continue an existing chat against the renamed project and inspect its working directory and writable roots.
  5. Attempt a normal, uniquely named temporary-file create/write/read/delete in the renamed repository.
  6. Compare the result with the same diagnostic from a newly created chat associated with that directory.

These are reconstructed steps from this incident, not a separately repeated clean-install reproduction.

Expected and actual behavior

Expected: Existing chats can be reassociated with the renamed project through supported UI, with the correct working directory and writable roots, without losing conversation context.

Actual during the audit: Project membership changed, but existing chats reported the old plumbing_inc working directory or writable root. They could read the new location but their normal temporary-file creation failed with PermissionError / Operation not permitted.

Impact and workaround

The user created eight replacement chats and recovered the original agents’ histories, decisions, requirements, and unfinished work. Original agents staged durable archives in a temporary directory for Engineering 2 to import into the renamed repository. This recovery required substantial coordination and carried a risk of lost context, missing attachments, and stale implementation claims. The workaround does not establish a supported repair path for an affected existing chat.

Suspected cause and requested diagnostics

Hypothesis: Per-chat workspace permissions or working-directory associations may remain tied to the original path after the project is removed and re-added. The internal root cause is not proven.

Please provide a supported way to reassociate existing chats with the renamed project and refresh their working directory and writable roots. Diagnostics should expose the project path, effective chat working directory, writable roots, and any stale association, with an actionable repair option. Investigating differences between original and fresh chats should help distinguish application state from filesystem access problems.
